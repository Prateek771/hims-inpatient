# MariaDB setup (branch `codex/mariadb-port`)

Status: work in progress, 6 November 2026. This branch ports the HIMS MVP from PostgreSQL to MariaDB 11.8 so it can run on Hostinger Business web hosting, whose database service is MariaDB. The PostgreSQL checkout (`codex/hims-development`, `web/drizzle/`) is unchanged and remains the source of truth until a reviewed cutover. No real patient data is authorized; see `AGENTS.md`. Design decisions and gaps: `docs/agent/MARIADB_PORT_CONVENTIONS.md`, `docs/agent/MARIADB_PORT_GAPS.md`, `docs/HOSTINGER_MARIADB_PLAN.md`.

## Local setup (Windows, no Docker)

1. Install MariaDB 11.8 (`winget install --id MariaDB.Server --version 11.8.2.0`), then restrict it to this PC by adding `bind-address=127.0.0.1` under `[mysqld]` in `data\my.ini` and restarting the service as Administrator.
2. From the `INS` folder run `powershell -NoProfile -File scripts/setup-local-mariadb.ps1`. It prompts for the root password privately, creates `hims_local` and `hims_test`, the accounts `hims_app`, `hims_test_owner` (full rights on `hims_test`) and `hims_test_runtime` (SELECT/INSERT/UPDATE/DELETE/EXECUTE), and writes the ignored `web/.env.mariadb.local`. It refuses to overwrite anything that exists.
3. `npm --prefix web ci`, then `npm --prefix web run db:migrate` applies `web/drizzle-maria/*.sql` in order and records each file's checksum in `hims_migrations`. Re-running is safe; a changed, already-applied file is refused.

## Schema files (`web/drizzle-maria/`)

| File | Content |
|---|---|
| `0001_tables.sql` | 98 tables, indexes, foreign keys, CHECK rules (`utf8mb4_nopad_bin`, UUID, `DATETIME(6)` in UTC) |
| `0002_helpers.sql` | 8 stored functions (use `DELIMITER $$`) |
| `0003_views.sql` | 6 `effective_*` views |
| `0004_triggers.sql` | Generated by `triggers/merge.mjs` from `T1`–`T5.sql` in PostgreSQL firing order |
| `0005_seed_rows.sql` | LangGraph checkpointer versions and fixed lock rows |

Edit `triggers/T*.sql` (T4 is generated by `T4.gen.mjs`) and run `node web/drizzle-maria/triggers/merge.mjs`; it also regenerates `web/src/server/expected-triggers.ts`, which the readiness check uses. Released migrations must not be edited: add a new numbered file instead.

## What differs from PostgreSQL

- **One database user.** Hostinger gives a single user, so append-only protection that PostgreSQL enforced with role grants is now enforced by triggers (`append_only_*`). The `hims_test_owner` account may bypass those guards to prepare fixtures.
- **Commit-time rules.** Seven deferrable constraint triggers cannot exist. Their rules run as explicit checks (`web/src/server/deferred-checks.ts`) before the commands commit; the stock/ledger rule is also an immediate trigger.
- **Locks.** `pg_advisory_xact_lock` is replaced by rows in `hims_locks` (`web/src/server/locks.ts`). `FOR SHARE` is sent as `LOCK IN SHARE MODE`.
- **Files.** Insurance documents and discharge PDFs are stored in the `protected_files` table, not on disk (hosting replaces the app folder on every deploy).
- **Paperwork checkpoints.** A MariaDB LangGraph saver (`web/src/server/insurance/mariadb-saver.ts`) replaces the PostgreSQL one.
- **Types.** Raw `execute` results go through `rowsOf` (booleans, UTC `Date` values); use `insertReturning`/`updateReturning` instead of `.returning()`.

## Checks

`npm --prefix web run test:unit` and `test:integration` run against the synthetic `hims_test` database, which is dropped, recreated and migrated when the schema files change and otherwise emptied in under a second. Browser tests and the backup/restore check are still being ported.
